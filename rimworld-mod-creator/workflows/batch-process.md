# 批量处理 Mod 需求

> **适用版本**: RimWorld 1.6 | **最后更新**: 2026-07-28

## 适用场景

当用户提供 `requirements.md` 需求清单，需要批量生成多个 mod 内容时使用本工作流。典型场景包括一次性添加多把武器、多套服装、多栋建筑等。

---

## 流程概览

```
读取需求文件 → 解析需求 → 逐个处理 → 用户确认 → 汇总输出
```

1. **读取需求文件**：读取用户提供的 requirements.md
2. **解析需求**：按需求标题分割，提取每个需求的类型和字段
3. **逐个处理**：根据类型加载模板，替换占位符，生成 Def
4. **用户确认**：展示每个生成的 Def，等待用户确认或修改
5. **汇总输出**：输出已确认和已跳过的清单，给出下一步指引

---

## 第一步：解析需求文件

### 需求文件格式

需求文件按以下格式编写（格式模板见 `templates/requirements-template.md`）：

```markdown
# Mod 需求清单

## 全局配置
- defName 前缀：XX（用户自行选择）
- 作者：用户自行填写
- packageId：用户自行填写

## 需求 1: 需求名称
- 类型：近战武器
- defName：XX_WeaponName
- label：中文名称
- 描述：中文描述
- 伤害：25
- 冷却：2.0
- 重量：1.5
- 材料：SteelBar, 10

## 需求 2: 另一个名称
- 类型：建筑
- ...
```

### 解析规则

按 `## 需求 N: <名称>` 分割需求，提取每个需求的：

| 提取字段 | 说明 |
|---------|------|
| 类型 | 近战武器/远程武器/建筑/服装/原材料/配方 |
| defName | 需求中指定的 defName |
| label | 显示名称 |
| 描述 | 描述文本 |
| 特有字段 | 根据类型不同，提取对应字段（见下表） |

### 类型 ↔ 特有字段对照表

不同类型的需求包含不同的特有字段：

| 类型 | 模板文件 | 特有字段 |
|------|---------|---------|
| 近战武器 | `templates/weapon-melee.xml` | 伤害、冷却、重量、伤害类型、可选：贴图 |
| 远程武器 | `templates/weapon-ranged.xml` | 伤害、冷却、射程、瞄准时间、连发数、弹药、重量、可选：贴图 |
| 建筑 | `templates/building.xml` | 尺寸、耐久、工作量、易燃性、美观度、建造材料、分类、可选：电力、研究前置 |
| 服装 | `templates/apparel.xml` | 护甲(钝击/穿刺/高温)、隔热(冷/热)、重量、覆盖部位、穿戴层、可选：贴图 |
| 原材料 | `templates/resource-stuff.xml` | 护甲系数、隔热系数、伤害系数、堆叠上限、重量、可选：贴图 |
| 配方 | `templates/recipe.xml` | 工作量、材料及数量、产出及数量、关联工作台 |

> 需求文件格式参考：`templates/requirements-template.md`

---

## 第二步：逐个处理

### 处理流程

对每个需求执行以下步骤：

1. **根据类型找模板**：从对照表确定对应的模板文件
2. **替换占位符**：将需求中的字段值填入模板对应位置
3. **生成 Def**：完成完整的 XML Def
4. **展示给用户确认**：输出生成的 Def 内容，等待用户反馈

### 替换占位符注意事项

- **defName**：确保包含用户选择的前缀，检查唯一性
- **label / description**：使用中文
- **数值参数**：对照需求中指定的数值，如未指定则使用模板默认值
- **texPath**：测试版可暂时引用原版贴图路径
- **costList / ingredients**：确保材料 defName 在原版或本 Mod 中已定义

### 处理顺序

建议按以下顺序处理，减少依赖问题：

1. 先处理原材料（其他物品可能引用）
2. 再处理武器/服装/建筑（可能依赖材料）
3. 最后处理配方（依赖物品 defName）

---

## 确认选项表

每个需求处理完成后，展示生成的 Def 并等待用户选择：

| 选项 | 含义 | 后续动作 |
|------|------|---------|
| 确认 | 生成的 Def 符合预期 | 记录到"已确认"清单，继续处理下一个 |
| 修改 | 需要调整部分内容 | 用户指出修改点，重新生成该 Def，再次确认 |
| 跳过 | 暂不处理此需求 | 记录到"已跳过"清单，继续处理下一个 |

展示格式示例：

```
### 需求 1: <名称>
类型：近战武器
生成的 Def：
[展示完整 XML]

请确认：
[1] 确认  [2] 修改  [3] 跳过
```

---

## 第三步：汇总输出

所有需求处理完成后，输出汇总报告：

### 汇总报告格式

```
## 批量处理汇总

### 已确认清单
- 需求 1: <名称> → <类型> → 已生成 Def
- 需求 3: <名称> → <类型> → 已生成 Def
- ...

### 已跳过清单
- 需求 2: <名称> → 用户选择跳过
- 需求 5: <名称> → 用户选择跳过
- ...

### 下一步指引
1. 所有已确认的 Def 已整合到 Mod 目录中
2. 请启动游戏测试已生成的物品/建筑
3. 测试方法：开启 DevMode → Spawn Thing / God Mode 建造
4. 如有问题，参考 workflows/debug-crash.md 排查
5. 测试通过后，可参考 workflows/formalize-mod.md 正规化
```

### 整合输出

- 将所有已确认的 Def 写入对应的 Mod 目录文件
- 如有配方依赖物品 defName，确认引用关系正确
- 如有贴图路径，确保路径一致性

---

## 注意事项

1. **每个需求独立生成**：每个需求独立处理，互不干扰，避免一个错误影响全部
2. **用户确认前不写入 Mod 目录**：所有生成的 Def 先在临时区域展示，用户确认后再统一写入
3. **全部确认后统一整合**：所有需求处理完成并确认后，一次性写入 Mod 目录文件
4. **检查跨需求依赖**：如果需求之间存在依赖（如配方引用物品 defName），在整合时验证引用关系
5. **保持前缀一致**：所有需求的 defName 必须使用统一的前缀
6. **贴图统一处理**：测试阶段统一引用原版贴图，正规化时统一替换为原创贴图
